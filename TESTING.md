# Testing Tabby

How to check that Tabby works and how to measure what it changes. The unit tests are fast and free; the evals run real `claude` sessions and cost money (about 1.3 cents per run on Haiku 5.5).

## Unit tests

```
python3 -m unittest discover tests
python3 tools/linkcheck.py
python3 tools/descriptions.py
```

They cover the hook gate (`scripts/gate.py`), the diff check (`scripts/guard.py`), `detect.py`, the installer, the shortcut ledger and the security findings validator. They need only the standard library.

## Evals

A case is a folder in `evals/` with a `prompt.md` (the request), a `fixture.sh` that builds a small repository, a `case.yaml` and `graders/`. The agent runs once with Tabby and once without; graders score what it left behind and what it did. Cases tagged `headroom` are built so the agent without Tabby is likely to fail.

### Check the environment before you trust a score

`claude plugin eval` runs the agent's Bash inside a bubblewrap sandbox (`bubblewrap` and `socat` must be installed). In that sandbox the network to PyPI is blocked, the home directory is read-only (so `uv run` cannot create its cache) and the Python on `PATH` is whatever is installed system-wide. If `pytest` and the packages the fixtures import (pydantic, fastapi, httpx, pandas and so on) are not installed there, the agent cannot run the tests in either arm, and every score measures that handicap, not Tabby. A first run in an unprepared container looked normal and was not. Before a full run, install the test dependencies into the system Python, run one case with `--keep-temp --runs 1`, and open the trace: look for a real `N passed` line from pytest and for the absence of `No module named pytest`, `Read-only file system` on the project's own commands, and `403 user denied` from pip. The `pricing-rule-laws` case also needs `hypothesis` installed, because the agent may use it and its hidden test runs the agent's tests. The "Read-only file system" line about a `cwd-` file in the temp folder is harness bookkeeping and harmless.

### Reading the results

`python3 tools/eval/summarise.py DIR` splits the cases. Those where the agent without Tabby already scores 0.95 or more are reported as no-regression checks. The headline delta uses the rest, with a 95% bootstrap interval and the list of cases where Tabby is worse by 0.10 or more. Five cases added in 0.2.0 target known failure modes: `type-error-no-ignore`, `reuse-existing-slugify`, `vague-request-asks-first`, `pydantic-v2-model` and `dry-run-flag-stays-small`.

### Ablation: which part gives which gain

Run `python3 tools/eval/make_arms.py arms/` and run the same cases against each arm with `run.py --plugin arms/<arm> --plugin-dir .`, then compare with `summarise.py --compare`. The arms are `full`, `no-gate` (core rules, no hooks that check), `gate-only`, `skills-only` and `core-only`. Not yet verified: that `claude plugin eval` runs a plugin's hooks. Check first with one cheap case (`--cases type-error-no-ignore --runs 1`) on `full` and on `skills-only`; if the two behave the same, the harness is not running hooks and the gate results mean nothing. Hidden tests, suppressions added, tests weakened and diff size come from `tools/eval/quality.py` (five cases added in 0.2.0 have hidden tests); blind pairwise judging of the diffs comes from `tools/eval/judge.py`, which now also scores `testable_structure`. Report the two separately: quality has parts a metric cannot see.

Every case is described in the [case catalogue](#case-catalogue) below. Case folders are in [`evals/`](evals/), the runner and summaries in [`tools/eval/`](tools/eval/).

## Scoring runs made without the ablation

`--ablation none` runs only the with-Tabby arm and scores every grader, including the plugin-fired indicator ("the skill was invoked") and graders marked with-only, which the paired runs leave out. To compare such a run with a paired one, rescore it: `python3 tools/eval/rescore.py DIR --like PAIRED_DIR`. It drops the indicator graders and every grader the paired run marked with-only. Before this was found, such runs were compared unscored-alike, which understated them by 0.013.

## Grader health

`summarise.py` ends with a grader-health line: how many graders never pass in any run of any arm ("dead") and how many always pass ("vacuous", so they cannot tell the arms apart). A dead grader is either broken (a glob path never matched; this hid four cases' scores until it was found) or asks for something no run reaches. Read one run's output to tell which. Plugin-fired indicators are skipped, since they fail without the plugin by design. On the 0.1.0 and 0.2.0 results, 35 graders are dead in both.

## Trigger sets

`evals/triggers.*.json` hold prompts and the skill each should load (`tools/eval/triggers.py`). `triggers.nearmiss.json` has 24 prompts that sound close to Python work but must load nothing (other languages, concept questions, installing tools). Add a near-miss for every wording you widen in a description, and keep some sets unseen while tuning descriptions (`heldout`, `holdout2`), so the descriptions are not fitted to them.
